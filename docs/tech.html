경기 데이터가
화면에 닿기까지

MLB 중계 데이터를 3초마다 읽어 질문을 열고, 판정하고, 정산 결과를 WebSocket으로 보냅니다. 단일 Spring Boot 서버와 PostgreSQL · Redis, React 화면, 그리고 운영에서는 꺼 둔 블록체인 기록 모듈로 이루어져 있습니다.

Architecture

서버 하나,
역할은 패키지로 나눴습니다

4주 일정에서 모듈을 나누는 비용 대신 단일 모듈 안에서 패키지 의존 규칙을 지켰습니다. 컨트롤러가 경기 추적 상태에 얽히지 않아야 라이브와 리플레이를 같은 코드로 돌릴 수 있습니다.

        리플레이 — 녹화한 경기를 같은 코드로

        경기가 없는 시간에도 시연하고 검증할 수 있도록 실제 경기의 응답을 녹화해 재생합니다. 분기하면 리플레이에서만 통과하는 버그가 생기므로, 공급원만 바꾸고 그 아래는 라이브와 같은 경로를 탑니다.

          Blockchain

          서버가 나중에 말을 바꿀 수 없게

          마감 시점의 참여 분포와 판정 결과를 Polygon 컨트랙트에 기록해, 운영자도 결과를 고칠 수 없다는 것을 증명하려는 설계입니다.

          운영 비활성 · CHAIN_ENABLED=false

          컨트랙트와 web3j 연동 코드는 구현했고, 컨트랙트는 Polygon Amoy 테스트넷에 배포해 소스 검증(Sourcify exact match)까지 마쳤습니다. 다만 운영 서버의 배포 구성에서는 체인 기록을 꺼 두었으므로, 서비스에서 열린 질문은 온체인에 기록되지 않았습니다. 아래 기록은 리플레이로 한 경기를 테스트넷에 끝까지 올린 실측입니다.

          Sourcify 검증 결과 Polygonscan (Amoy)

            컨트랙트가 지키는 다섯 가지 BaseballPredictionMarket.sol

              업그레이드 프록시를 쓰지 않습니다. 로직을 바꿀 수 있으면 위 다섯 가지가 "지금은 안 바꾸겠다는 약속"으로 격하되므로, 버그가 나면 고쳐서 재배포하고 이전 주소의 기록은 그대로 둡니다.

              사용자 경험은 체인을 기다리지 않습니다

                • nonce 잠금 — 지갑이 하나라 두 경기가 동시에 기록하면 같은 nonce로 서명할 수 있어, 전송 지점을 잠금으로 감쌌습니다. 실측에서 약 3초 대기가 실제로 걸리는 것을 확인했습니다.
                • 잔액 가드 — 리허설에서 잔액이 떨어져 16개 중 13개만 기록된 적이 있습니다. 경기를 끝까지 기록할 수 없으면 시작 전에 끕니다. 절반 기록보다 무기록이 설명 가능합니다.
